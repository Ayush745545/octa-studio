The module is split into three layers inside `app/publishing/`:
- UI layer (`page.tsx`): a Next.js Server Component that reads connected channels and the publication queue from Prisma and renders them with shared `@/components/publishing/*` components.
- Action layer (`actions/`): Next.js Server Actions (`schedule-publication`, `reschedule-publication`, `cancel-publication`, `toggle-channel`) that validate inputs, mutate `publication`/`content` rows in Prisma (using `$transaction` where multiple tables must stay consistent), and call `revalidatePath` on every route that displays publication state.
- Engine layer (`engine/`): a platform-agnostic distribution pipeline. `types.ts` defines the `PublishingProvider` interface (`platform`, `publish(input, context) => PublishResult`). `providers/index.ts` registers concrete providers in a `Record<string, PublishingProvider>` keyed by platform string and exposes `getPublishingProvider(platform)` which throws if no provider is configured. Two providers exist: `simulated.ts` (logs and returns a fake `externalId`) and `linkedin.ts` (implements LinkedIn REST API image upload + post creation using stored `accessToken`/`authorUrn`). `process-scheduled.ts` is the cron/scanner entry point that polls `publication` rows with `status = 'SCHEDULED'` and `scheduledAt <= now`, then delegates each to `publishPublication` (from `publish.ts`) to invoke the resolved provider.
Dependency direction is strictly one-way: actions depend on Prisma only; the engine depends on the provider registry; the page depends on actions via client components but never touches the engine directly.
